# Architecture

```
┌──────────────────────── Voice Studio (one process, Rust + Tauri 2) ─────────────────────────┐
│ WebView UI (ui/, vanilla TS)                                                                │
│   legend + highlighted editor · engine/voice · toggles · MAKE · batch queue · player        │
│        │ invoke / events                                                                    │
│ src-tauri (commands.rs) ── mpsc ──► render-worker thread (owns Studio, one job at a time)   │
│        │                                   │                                                │
│        │                            vs-core::render::Studio                                 │
│        │                   parse → plan → [cache?] → synth → trim/fade → stitch → LUFS      │
│        │                       │                          │                                 │
│        │              Kokoro (ort, in-process)    Chatterbox client ──stdin/stdout JSON──┐  │
│ download threads (ureq, Range resume, SHA-256)        Job Object (Windows), parent watch │  │
└──────────────────────────────────────────────────────────────────────────────────────────┼──┘
                                                         isolated Python worker (venv, uv) ◄┘
                                                         torch 2.6 · chatterbox-tts 0.1.7
```

## Crates

| Path              | What                                                                                     |
|-------------------|------------------------------------------------------------------------------------------|
| `crates/vs-core`  | Everything testable without a window: markup, G2P, engines, audio DSP, projects, cache, queue, downloads, catalog, voice profiles, Python runtime manager, diagnostics. |
| `crates/vs-cli`   | `vscli`: headless front-end over the same core (install models, render, batch, bench, diagnostics). Used by CI and for benchmarks. |
| `src-tauri`       | Desktop shell: Tauri commands, worker thread, event emission, logging.                  |
| `ui`              | Front-end (Vite + TypeScript, no framework). `ui/dev/preview.ts` is a browser-only preview with mocked IPC. |
| `worker`          | `chatterbox_worker.py`, embedded into the binary and written to the runtime folder.     |
| `catalog`         | `packages.json` (downloadable files with upstream SHA-256, generated by `scripts/gen_packages.py`) and `models.json` (24 evaluated models). |

## Idle behaviour

* Nothing is loaded at startup. The first MAKE loads the selected engine; it is unloaded after
  the idle timeout (default 5 min, configurable) or immediately via Diagnostics › Unload.
* The worker thread blocks on a channel with a 15 s timeout (only to check the idle timer).
* The player's spectrum uses `requestAnimationFrame` only while audio plays.
* Measured idle CPU after start-up settles: ~0.1 % of one core (see BENCHMARKS.md).

## Engines

**Kokoro** — `ort` 2.0 with `load-dynamic`: ONNX Runtime is a downloadable package (CPU, or
DirectML on Windows, CoreML on macOS), so the installer stays ~3–5 MB. Text is converted to
misaki phonemes by a Rust port of misaki's lexicon path (gold/silver dictionaries, function
word context rules, -s/-ed/-ing stemming, numbers/currency/years/times), with compound
splitting and NRL letter-to-sound rules for unknown words. Device "auto" = CPU because on the
test machine DirectML was not faster and costs ~5 s of graph compilation per load.

**Chatterbox** — runs in a separate Python process inside a venv created by uv (Python 3.11,
torch 2.6 CUDA 12.4 / CPU / MPS, chatterbox-tts 0.1.7, setuptools<81 for the watermarker).
The process is crash-isolated: a crash or cancel kills only the worker; it is bound to a
kill-on-close Job Object on Windows and also exits when stdin closes or the parent PID
disappears. Offline is enforced with `HF_HUB_OFFLINE=1`; weights are loaded from the model
folder with `from_local`. Speaker conditioning is cached per reference file (path, mtime,
size); a fixed seed per project keeps identity stable across segments.

## Rendering pipeline

1. `markup::parse` → styled spans (byte offsets, warnings).
2. `render::plan` → segments: same-emotion spans merge, sentences split and packed
   (≤320 chars Kokoro, ≤220 Chatterbox), very long sentences split at clauses. The plan is
   checked to reproduce the parsed word sequence exactly, otherwise rendering aborts.
3. `engine::plan_style` maps emotion → engine controls and labels each as genuine /
   approximate / unsupported.
4. Per segment: cache key = SHA-256 of {cache version, model fingerprint (weights hash),
   voice or reference hash, seed, text runs, style parameters, sample rate}. Hit → read the
   cached float WAV; miss → synthesize and store.
5. DC removal, silence trim (−50 dBFS), style gain, 6 ms raised-cosine fades, explicit pause
   silence (or equal-power crossfade for zero gaps).
6. ITU-R BS.1770-4 integrated loudness normalization (default −16 LUFS) + look-ahead peak
   limiter (−1 dBFS).
7. Project folder: `project.json` (schema v1), `script.txt`, `segments/NNN.wav`,
   `reference.wav` (when cloning), `final.wav`, optional `final.mp3` (FFmpeg/LAME),
   `render.log`.

## Persistence and safety

* All JSON state is versioned (`schema_version`) and written atomically (temp file + fsync +
  rename). Corrupt settings fall back to defaults and are kept as `settings.json.bad`.
* User-controlled names go through `sanitize_file_name`; archive extraction and package paths
  go through `safe_join`; deletes are restricted to the model/projects/voices roots.
* `read_audio` only serves `.wav/.mp3` files inside Voice Studio folders.
* Downloads resume with HTTP Range, retry with back-off, and are accepted only when the
  SHA-256 matches the catalog. A package is "installed" only once its manifest is written.
* The batch queue is persisted; jobs that were running during a crash are resumed and their
  finished segments come from the cache.
* Settings, models, runtimes, voices and cache live in `%LOCALAPPDATA%\VoiceStudio`
  (`~/Library/Application Support/VoiceStudio`, `~/.local/share/VoiceStudio`), never in the
  install directory, so they survive updates. `portable.txt` next to the exe switches to a
  `VoiceStudioData` folder beside it. `VOICE_STUDIO_HOME` overrides both.
